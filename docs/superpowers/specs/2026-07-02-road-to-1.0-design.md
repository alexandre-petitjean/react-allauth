# Road to 1.0 — improvement plan

Date: 2026-07-02
Status: approved

## Goal

Take `react-allauth` from 0.1.0 to a stable, well-tested 1.0.0 by hardening
tests, adding end-to-end coverage against the real playground backend,
auditing the public API, and shipping user-facing documentation. Feature
extensions (SSR, React Native, UI components) are explicitly out of scope
until after 1.0.

## Context

The library is in good shape for a 0.1.0: 8 public hooks, all typed and unit
tested (28 tests via Vitest + MSW), CI on Node 20/22, npm publishing with
provenance, a Dockerized Django playground backend, threat model and
versioning policy. The weak spots: thin coverage on several hooks
(`useSessions`: 1 test, `useWebAuthn` / `useConfig`: 2 each), no direct tests
for `client.ts` or `useResource`, no e2e tests, no documentation site, and an
API contract still declared unstable.

## Plan

### Phase 1 — Quick hygiene wins

- Remove the obsolete `--passWithNoTests` flag from the `test` script.
- Enable Vitest coverage (v8 provider) with a threshold enforced in CI
  (85% lines/statements on `src/`, raised as phase 2 lands).
- Add Dependabot configuration (npm + GitHub Actions ecosystems).
- Add a short `CONTRIBUTING.md` (setup, scripts, pre-commit, PR conventions).

### Phase 2 — Strengthen unit tests

- Fill coverage gaps in `useSessions`, `useWebAuthn`, `useConfig` and
  `useSocialAuth`: error channels, 401 / session-expired paths, interrupted
  flows, non-JSON replies.
- Add direct tests for `client.ts`: CSRF header wiring, cookie handling,
  transport errors (`AllauthTransportError`), envelope parsing.
- Add direct tests for `useResource`: stale-response protection, reload
  races, fetcher identity changes.

### Phase 3 — End-to-end tests against the real backend

- Add Playwright with a small suite driving the playground UI against the
  Dockerized django-allauth backend (`playground/backend/docker-compose.yml`).
- Scenarios: login/logout, signup + email verification, TOTP setup and
  challenge, password reset by key, session listing and revocation.
- New CI job: boot the backend via docker compose, run the e2e suite on PRs
  and master.

### Phase 4 — API audit and contract freeze

- Review the 8 hooks for consistency: naming, return shapes, uniform
  error channel, loading semantics.
- Apply any resulting breaking changes in one batch, documented in the
  CHANGELOG under a 0.x minor.
- Prepare (not publish) a `1.0.0-rc` entry: the maintainer triggers the
  actual release by pushing the version tag.

### Phase 5 — Documentation

- VitePress site under `docs/site/`: getting started, one guide per hook,
  backend configuration guide (`HEADLESS_ONLY`, CORS, cookies, CSRF), error
  handling guide.
- Deploy via GitHub Pages workflow.
- Link the site from the README.

### Phase 6 — Release 1.0.0 (manual gate)

- After the RC has soaked, finalize CHANGELOG, bump to 1.0.0, tag and push.
- This step is executed by the maintainer, not automated by this plan.

## Success criteria

- CI enforces a coverage threshold; all previously thin hooks have error-path
  tests.
- An e2e suite passes against the real backend in CI.
- The public API is consistent and frozen; VERSIONING.md reflects the RC.
- A published documentation site covers every hook and backend setup.

## Out of scope

- SSR / Next.js server components support.
- React Native / token-based (cookieless) client.
- Prebuilt UI components.
